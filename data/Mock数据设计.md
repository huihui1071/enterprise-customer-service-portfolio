# Mock 数据设计

## 1. 数据原则

- 所有姓名、机构、病例、工单和运行记录均为虚构。
- 不使用真实患者姓名、联系方式、影像或医疗详情。
- 正常业务数据、边界数据和故障注入配置分开保存。
- 固定随机种子，确保数据和评测结果可复现。
- ID 格式稳定，便于演示、调试和自动化断言。

## 2. 数据分层

### 2.1 Seed

系统正常启动与演示所需的基础数据：

- 10 个机构；
- 30 个医生；
- 15 个助理；
- 8 个客服；
- 2 个管理员；
- 约 200 个病例及状态事件；
- 约 100 个工单及工单事件；
- 用户机构任职关系和助理医生授权关系。

### 2.2 Boundary

系统必须稳定处理的特殊业务数据或输入：

- 冻结、禁用和离职用户；
- 暂停和关闭机构；
- 过期、撤销的助理授权；
- 跨机构和非本人病例查询；
- 不存在及格式错误的病例号；
- 资料缺失、暂停、取消和完成病例；
- 无关联病例的工单；
- 重复幂等键请求；
- 已解决后重新处理、用户失联关闭等工单流转。

### 2.3 Fault

通过独立故障配置或请求参数触发，不混入正常业务记录：

- API 超时；
- 数据库暂时不可用；
- `400/401/403/404/409/429/500`；
- 返回体不符合 JSON Schema；
- 模型或工具超时；
- 知识库无召回；
- 上下文状态过期。

## 4. ID 规范

| 对象 | 示例 |
|---|---|
| 用户 | `USR-DOC-001`、`USR-AST-001`、`USR-SPT-001` |
| 机构 | `ORG-001` |
| Membership | `MEM-0001` |
| 授权 | `ASG-0001` |
| 病例 | `CASE-2026-0001` |
| 病例事件 | `CSE-000001` |
| 工单 | `TKT-2026-0001` |
| 工单事件 | `TKE-000001` |

ID 不编码真实身份或医疗信息。角色前缀仅用于作品集调试，后续可说明生产系统应使用不可预测标识。

## 5. 关键覆盖配额

### 用户与权限

| 情况 | 最少数量 |
|---|---:|
| 正常在职医生 | 24 |
| 离职医生 | 3 |
| 冻结或禁用医生 | 3 |
| 正常助理 | 11 |
| 无授权助理 | 2 |
| 授权过期或撤销助理 | 2 |
| 跨机构测试关系 | 4 组 |

### 病例

| 情况 | 建议数量 |
|---|---:|
| 正常主流程各状态 | 140 |
| 已暂停 | 15 |
| 已取消 | 10 |
| 已完成 | 20 |
| 离职医生历史病例 | 5 |
| 冻结医生负责病例 | 5 |
| 跨机构权限测试病例 | 5 |

病例总数目标为 200；同一病例可以同时属于状态覆盖和权限边界覆盖，避免为了凑数制造重复数据。

### 工单

| 情况 | 建议数量 |
|---|---:|
| 普通知识、流程和系统问题 | 45 |
| 病例状态相关 | 15 |
| 高风险临床异常 | 20 |
| 投诉或其他问题 | 10 |
| 无关联病例 | 10 |

工单状态覆盖 `open`、`processing`、`pending_user`、`resolved` 和 `closed`，并至少包含 5 个重新处理事件和 5 个非成功关闭原因。

## 6. 必须可复现的业务断言

1. 在职医生可以查询本人负责的同机构病例。
2. 同机构医生不能默认查看其他医生病例。
3. 助理必须同时具有有效 Membership 和 Assignment。
4. 离职医生、冻结用户和跨机构用户不能查询目标病例。
5. 不存在与无权限病例使用相同对外提示，内部原因码不同。
6. 同一个 `idempotency_key` 重试不会生成第二张工单。
7. 终态病例和工单不能通过普通接口非法回退。
8. 高风险工单创建后立即分派高风险人工团队。

# 项目背景与用户研究

## 1. 文档状态

- 项目类型：模拟企业项目 / 作品集
- 当前版本：v0.1
- 数据属性：全部为模拟假设
- 目标读者：产品、工程、面试官和作品集评审者

## 2. 背景假设

某隐形矫治企业向合作诊所提供产品、病例设计、生产交付、系统工具和培训服务。合作医生与诊所助理在日常工作中会产生大量高频咨询，当前主要由人工客服承接。

模拟现状如下：

| 指标 | baseline_assumption |
|---|---:|
| 日均有效咨询量 | 2,200 次 |
| 平均首次响应时间 | 8 分钟 |
| 平均人工处理时间 | 6.1 分钟 |
| 人工一次解决率 | 85% |
| 高峰期排队时间 | 15-30 分钟 |
| 跨客服答案一致率 | 80% |
| 月均可标准化重复咨询人工量 | 约 2,900 小时（按总人工量的 60%、每月 22 个服务日估算） |

这些数值用于支持产品推演，不代表真实公司数据。

## 3. 问题定义

### 3.1 用户问题

- 高频标准问题仍需等待人工回复。
- 服务流程、产品版本和系统操作的信息分散，查找成本高。
- 同一问题可能因客服经验不同得到不同表述。
- 病例异常或临床风险问题可能被普通咨询队列延误。
- 医生和助理查询病例状态时，需要在多个系统之间切换。

### 3.2 业务问题

- 人工客服大量时间消耗在可标准化问题上。
- 高峰期容量依赖排班，扩容成本高。
- 缺少统一的问题分类、失败归因和知识反馈闭环。
- 自动化若缺乏权限和风险边界，可能放大医疗信息与隐私风险。

### 3.3 产品机会

建立人机协同的智能客服：AI 优先处理低风险、知识边界清晰、可评测的问题；高风险、低置信度、权限不足和工具异常场景交给人工。

## 4. 用户画像

### 4.1 合作医生

**目标**

- 快速获得产品、流程和临床术语解释。
- 查询自己负责病例的当前状态。
- 发生异常时快速进入临床支持流程。

**约束**

- 同时管理多个病例，不能依赖“最近病例”自动推断查询对象。
- 工作时间碎片化，需要短、准、可执行的回复。
- 临床相关回答必须明确边界，不能替代诊断。

**JTBD**

> 当我在接诊、提交方案或复诊过程中遇到问题时，我希望快速得到有依据的说明或正确进入支持流程，从而不中断当前工作，也不泄露或误查病例信息。

### 4.2 诊所助理

**目标**

- 查询流程、系统操作、物流与培训资料。
- 帮医生准备病例材料和跟进处理状态。

**约束**

- 对临床术语理解有限，需要步骤化表达。
- 访问病例必须受机构与授权关系约束。
- 高频操作问题需要可以直接执行的指引。

**JTBD**

> 当我协助医生处理病例和诊所事务时，我希望按步骤得到准确指导，并知道下一步去哪里操作或联系谁，从而减少重复询问客服。

### 4.3 人工客服与临床支持人员

**目标**

- 减少重复问题。
- 优先处理需要判断、协调或承担风险的任务。
- 接手时获得完整上下文，不让用户重复描述。

**JTBD**

> 当 AI 无法安全解决问题并转交给我时，我希望立即看到用户身份、问题摘要、病例号、风险原因和已执行步骤，从而快速继续处理。

### 4.4 运营与管理员

**目标**

- 管理知识版本、风险规则和场景开关。
- 查看质量、采用率、成本与 bad case。
- 审计敏感查询和工具操作。

## 5. 为什么适合 AI

| 判断维度 | 结论 |
|---|---|
| 频次 | 六类问题重复度高，具备规模价值 |
| 结构 | 知识问答半结构化，纯规则难以覆盖自然语言变体 |
| 数据 | 可构造知识、接口和评测数据闭环 |
| 可评测性 | 路由、召回、回答、工具和转人工均可定义期望结果 |
| 风险 | 风险差异明显，适合分层自动化而非全自动 |

## 6. 为什么不只用纯规则

纯规则适合病例号格式、权限判断、风险硬规则和接口状态处理，但不擅长处理同义表达、多意图、上下文和自然语言答案组织。

目标方案采用混合架构：

```text
确定性规则：身份、权限、病例号、风险硬规则、接口错误
LLM：意图理解、槽位补全、问题摘要、基于证据的回答生成
RAG：产品、流程、系统、术语和培训知识
人工：临床判断、投诉、高风险异常、权限争议和低置信度问题
```

## 7. 用户研究限制

本阶段没有真实访谈对象，因此画像和 JTBD 属于待验证假设。后续作品集应明确说明：真实企业项目中需要通过访谈、客服日志分析和跟岗观察验证，而本项目通过模拟日志和 Eval 数据验证系统行为。

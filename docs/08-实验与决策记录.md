# 实验与决策记录

| 决策/问题 | 证据或实验 | 结论 | 状态 |
|---|---|---|---|
| 病例查询是否自动化 | 高频、结构化、可鉴权 API 确定性获取 | 自动化，但必须补参和对象鉴权 | 已实现 Backend |
| 临床异常是否由 AI 回答 | 风险高且错误代价高 | AI 只识别、收集最小证据并立即转人工 | 已实现 Backend 建单规则 |
| RBAC 是否足够 | 同机构医生仍可能横向访问他人病例 | 增加 Membership、Assignment 和对象归属校验 | 8/8 权限用例通过 |
| 工单重试是否会重复创建 | 模拟相同幂等键重复请求 | 同键同请求返回原工单；冲突请求返回 409 | 测试通过 |
| 403/404 是否应区分 | 区分会泄露病例是否存在 | 对外统一提示，对内审计真实原因 | 测试通过 |
| 产品问答出现病例号追问 | Dify 复现并检查 DSL | 删除错误 ELSE 并行边 | 云端草稿已修复 |
| 明确病例查询进入知识库 | 检查条件变量类型 | `status_query_hint` 改为 boolean | 云端草稿已修复 |

| HTTP 结果 Prompt 输出模板占位符 | Prompt 中变量是手输文本 | 重建 Prompt 并插入 HTTP `body` 变量 | 云端草稿已修复 |
| 原 Demo ID 与新版数据契约不一致 | Dify 使用 `A...`/`T...`，Backend 使用 `CASE...`/`TKT...` | 用隔离的 Demo Adapter 做双向映射，核心 API 保持统一契约 | 公网验证通过 |

| 用户切换到“另一个病例”后能否复用旧病例 | 首次回归发现只清理 `active_case_id`，仍会由 `confirmed_case_id` 恢复旧病例 | 待补病例号分支同时清理活动病例和已确认病例；后续指代必须重新提供病例号 | 云端草稿回归通过 |

## 指标口径

- `target`：基于模拟业务设定的目标，不能表述成线上结果。
- `measured`：由固定数据集与脚本可复现的结果。
- `unmeasured`：尚未完成 Dify 公网端到端接入的指标。

## 发布门槛

- 越权成功数必须为 0。
- 高风险漏转人工属于阻断发布问题。
- API 返回不确定时不得生成确定性病例结论。
- Dify 草稿必须完成固定回归集并经人工确认后发布。
# 2026-08-23：会话记忆证据分层

- **决策**：将确定性记忆策略、Dify 浏览器冒烟和批量模型 Eval 分开计量。
- **原因**：状态机契约通过不代表 Dify 节点连线正确，少量浏览器冒烟通过也不代表总体准确率。
- **实现**：新增 15 条可执行记忆契约评测，覆盖补参、任务切换、单/多病例指代、10 轮过期、权限撤销、高风险抢占和工单/病例实体隔离。
- **当前证据**：Backend 指标来自自动化测试；Dify 主链路和核心记忆来自浏览器逐条实测；路由、RAG、引用和延迟总体指标仍保持为目标值。

# 2026-08-23：Dify 画布恢复与代码同步

- **现象**：地址为 `/workflow`，一度显示 API 页面；恢复画布后点击节点仍不打开配置抽屉。
- **原因**：浏览器会话中存在失效页面对象，Dify 前端同时记录了数据订阅被取消的 `AbortError`；恢复后画布停留在手模式，且目标节点位于视口外约 `x=-629, y=-74`。
- **恢复**：重建浏览器控制连接、标准路由刷新、将画布平移回节点区域并切换到指针模式；节点配置抽屉恢复正常。
- **同步**：云端归一化 Code 节点已覆盖为仓库同源代码，新增 `case_reference_status_next`、`recent_case_ids_next`、`next_turn` 三个输出。
- **写入**：病例鉴权成功后写入最近病例列表、最后确认轮次和指代状态；显式病例查询回归成功，检查清单显示所有问题均已解决。
- **边界**：当时公共轮次递增节点和多病例歧义分支尚未接线；后续已补齐并实测，草稿仍未发布。

# 2026-08-23：病例接口错误、超时与失败记忆清理

- Demo Adapter 在显式开启 `ENABLE_FAULT_INJECTION` 时接受 `X-Fault-Mode`，Dify 归一化节点仅将作品集测试词 `ERR400/401/403/404/409/429/500` 与 `TIMEOUT` 映射到该请求头；正常用户请求输出空值。
- 病例 HTTP 节点设置 5 秒连接、读取和写入超时，保留 3 次重试，并启用异常分支；异常时只返回“暂时无法获取”，不让 LLM根据旧上下文猜测病例状态。
- 异常回复后使用确定性空值输出清理 `active_case_id`、`confirmed_case_id` 和 `recent_case_ids`，使技术故障和权限拒绝后的回指都必须重新提供病例号并重新鉴权。
- 云端逐条通过正常查询、`500`、`TIMEOUT`、无权病例及失败后旧病例回指，共 `5/5`；工单创建与查询仍需增加等价异常分支。

# 2026-08-23：工单创建与查询故障降级

- `创建工单` 与 `查询工单` 均接入受控 `X-Fault-Mode`，连接、读取和写入超时设为 5 秒，保留 3 次重试并启用异常分支。
- 高风险建单失败时明确告知“人工工单暂未创建成功”，不把异常回复表述成已完成转人工；同时保留线下急救和人工客服安全提示。
- 工单查询失败时只返回暂不可用，并明确声明不会猜测工单状态，避免由 LLM 根据历史上下文生成虚假进展。
- 云端逐条通过正常建单、建单 `500`、建单 `TIMEOUT`、正常查单、查单 `500`、查单 `TIMEOUT`，共 `6/6`。草稿未发布。

# 2026-08-23：权限变化后的记忆清理

# 安全与权限设计

## 1. 威胁重点

- 用户伪造请求正文中的 `doctor_id` 或 `organization_id`。
- 同机构医生枚举并访问其他医生病例。
- 助理访问未获授权医生病例。
- 离职、冻结或跨机构用户继续访问历史对象。
- 通过 403/404 差异枚举真实病例号。
- Dify 超时重试产生重复高风险工单。
- 提示注入诱导系统忽略权限或输出敏感数据。

## 2. 防护层次

```text
JWT 可信身份
→ User 账号状态
→ Organization 状态
→ Membership 角色、状态和有效期
→ AssistantDoctorAssignment
→ Case/Ticket 对象级权限
→ 最小字段响应
→ 审计日志
```

角色授权只解决“某类用户通常能做什么”，对象鉴权继续解决“该用户能否操作这一条具体记录”。

## 3. IDOR 防护

- 资源接口只信任 JWT `sub`，忽略请求参数中企图覆盖身份的字段。
- 医生仅能读取 `primary_doctor_user_id` 与自身匹配的病例。
- 助理必须同时具有有效 assistant Membership 和 Assignment。
- 病例不存在与无权限使用相同对外提示，内部审计保留不同原因码。
- 每次允许与拒绝均记录 `trace_id`。

## 4. 工单安全

- 每次建单必须提供 `Idempotency-Key`。
- 同一键和相同请求返回原工单；同一键对应不同请求体返回 `409`。
- 高风险工单只做升级和证据交接，AI 不提供诊断或治疗建议。
- 故障重试复用原幂等键，避免生成重复工单。

## 5. 当前边界

- 全部数据为模拟数据，不接入真实患者或公司系统。
- 默认开发密钥不可用于外部部署。
- SQLite 适合本地作品集，不代表生产数据库选型。
- 正式部署需增加密钥托管、TLS、Token 撤销、速率限制、数据库备份和集中日志。

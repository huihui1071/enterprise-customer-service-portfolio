# 企业级智能客服 PRD

## 1. 产品概述

面向合作医生和诊所助理，提供知识问答、病例状态查询、工单查询和高风险转人工能力。系统采用规则、LLM、RAG、业务 API 与人工协作的混合方式。

## 2. 产品目标

### 2.1 用户目标

- 低风险高频问题获得快速、一致、有依据的答案。
- 病例状态在身份和归属校验后可查询。
- 高风险问题被及时识别并携带上下文转交人工。

### 2.2 业务目标

- 降低重复咨询人工量。
- 缩短首次响应时间。
- 提高答案一致性和处理过程可追溯性。
- 建立可持续的 Eval 和 bad case 闭环。

### 2.3 安全目标

- 病例越权访问成功数为 0。
- 高风险问题不得被普通知识答案覆盖。
- 任何工具操作均可关联身份、会话和审计记录。

## 3. 产品范围

### 3.1 MVP 范围

- 医生和助理模拟登录。
- 五个知识域的 RAG 问答。
- 病例号识别与多轮补充。
- 病例状态结构化查询。
- 高风险识别与人工工单创建。
- 工单状态查询。
- 低置信度、无知识和 API 故障兜底。
- 运行日志、用户反馈和 Eval 数据采集。

### 3.2 非目标

- 真实患者服务。
- 临床诊断或治疗建议。
- 真实支付、退款、物流和生产系统。
- 自动修改病例、治疗方案或用户权限。
- 语音客服和多渠道正式接入。

## 4. 核心用户故事

### US-01：知识问答

作为医生或助理，我希望询问产品、流程、系统、术语或培训问题并看到可靠来源，以便快速继续工作。

**验收标准**

- 正确路由到一个知识域，不产生无关分支输出。
- 仅使用有效状态和适用角色的知识。
- 回复包含结论、必要说明、下一步和真实引用 metadata。
- 无有效证据时不编造答案。

### US-02：病例状态查询

作为已登录用户，我希望查询自己有权限查看的病例状态，以便了解下一步安排。

**验收标准**

- 缺少病例号时只追问一次并保存待办状态。
- 病例号由用户确认，不根据记忆直接选定。
- API 使用可信 Token 中的身份，不信任请求正文中的 `doctor_id`。
- 无权限返回安全提示，不泄露病例是否存在及具体信息。
- 状态来自 API，不来自知识库或模型推测。

### US-03：高风险异常升级

作为医生或助理，我希望临床异常被优先处理，以便及时获得人工支持。

**验收标准**

- 高风险硬规则优先于普通意图分类。
- 系统只做风险分流，不给诊断或治疗建议。
- 信息足够时创建一个且仅一个工单。
- 信息不足时只收集必要字段，避免额外敏感信息。
- 返回工单号、优先级、处理团队和预期下一步。

### US-04：工单查询

作为提交过问题的用户，我希望查看有权限的工单状态，以便知道是否需要补充信息。

**验收标准**

- 校验工单归属。
- 展示当前状态、更新时间和下一步。
- 不展示内部敏感备注。

### US-05：人工接管

作为客服或临床支持人员，我希望接收结构化摘要，以便无需让用户重复描述。

**验收标准**

- 摘要包含用户角色、机构、问题、病例号、风险原因和已执行步骤。
- 不包含无关敏感信息。
- 人工处理结果可回写工单。

## 5. 核心决策规则

路由优先级固定为：

```text
身份/输入校验
> 高风险硬规则
> 待办会话续接
> 工单查询
> 病例状态查询
> 知识意图分类
> fallback
```

同一轮只允许一个面向用户的主输出。后台记录和工单操作可以并行，但不能产生多个相互冲突的回复。

## 7. 非功能需求

- 安全：JWT、RBAC、对象归属校验、审计、敏感字段脱敏。
- 可靠性：重试、超时、幂等、降级、健康检查。
- 性能：知识问答 P95 首次响应不超过 8 秒。
- 可观测性：记录 trace_id、路由、工具、模型、知识版本、延迟和错误码。
- 可测试性：每条 P0 链路具有自动化正向、反向和故障测试。
- 可维护性：Prompt、schema、风险规则和接口版本化。

## 8. 发布策略

```text
离线 Eval 达标
→ 内部测试账号灰度
→ 仅开放低风险知识问答
→ 开放病例只读查询
→ 开放高风险自动建单
→ 根据护栏指标决定扩大或回滚
```

本作品集不进行真实业务发布。Dify 新版本发布前需人工确认。

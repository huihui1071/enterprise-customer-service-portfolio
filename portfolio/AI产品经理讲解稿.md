# AI 产品经理讲解稿

## 面试调研结论

真实面经中，AI 产品经理通常不是只考 PRD，而是连续追问：项目为什么做、用户和价值是否真实、为何选这个模型或方案、RAG/Agent 怎么设计、效果如何评估、数据从哪里来、Bad Case 怎么修、上线结果是否可信，以及候选人能否理解模型边界。

## 90 秒版本

我做了一个面向合作医生和诊所助理的企业级智能客服模拟项目。最关键的产品判断不是“哪些问题都让 AI 回答”，而是根据频次、结构化程度、事实确定性、风险和容错成本划分自动化边界。

病例状态查询高频且数据结构明确，可以通过多轮补齐病例号，再调用鉴权 API，因此适合自动化。临床异常同样是 P0，但风险高、容错成本高，所以 AI 只负责高风险识别、最小证据收集和人工升级，不做诊断。优先级决定先解决什么，自动化边界决定 AI 可以负责到哪里。

我完成了六类场景、PRD、状态机、权限规则、指标树和 150 条 Eval，并用 Bad Case 驱动路由和兜底迭代。当前固定合成集综合 Eval 为 150/150，execution error 和 release blocker 都是 0，P50 5.58 秒、P95 8.26 秒；Backend 权限决策 8/8，越权成功数为 0。这个结果证明原型在固定契约下可复现，不代表真实生产准确率 100%。

## 高频追问与最佳回答

### 一、项目与产品判断

**1. 请系统介绍这个智能客服项目。**

我按“问题、判断、方案、证据”来介绍。问题是重复知识咨询和病例进度查询占用人工，而临床异常又要求快速、安全地升级。产品判断是把确定性任务与高风险任务拆开：知识问答走 RAG，病例查询走鉴权 API，临床异常只识别和转人工。方案由 Dify 负责路由、RAG 和会话状态，FastAPI 负责权限、病例事实和幂等建单。最后用 150 条固定合成 Eval 验证，而不是只演示几条成功对话。

**2. 为什么选择这六类场景，数据从哪里来？**

六类一级场景是产品咨询、服务流程、系统使用、临床术语/设计说明、培训资料、病例状态/异常升级。它们来自项目假设的用户任务地图，能覆盖知识、结构化查询和高风险升级三种解法。日均 2,200 次、频次和人工耗时都是 `baseline_assumption`，不是时代天使真实数据；Mock 实体、边界和故障样本由数据模型与测试目标生成，实测结果则来自版本化脚本和报告。

**3. 你如何定义用户问题和核心价值？**

核心用户是合作医生和获授权助理。医生的 JTBD 是在不切换多个系统的情况下快速获得可信的流程、产品和病例信息；助理还要在医生授权范围内代为查询。价值不是“有一个聊天机器人”，而是减少重复查询时间、缩短首次响应，同时不牺牲权限和临床安全。

**4. 为什么病例查询和临床异常都是 P0，却走不同路径？**

P0 表示优先解决，不等于优先自动化。病例查询高频、结构化、事实可从接口确定获取，适合补参后自动闭环；临床异常风险高、误答代价高，AI 应识别、收集证据并升级人工。自动化边界由结构化程度、事实确定性和错误代价共同决定。

**5. 如何确定优先级？为什么不先做所有知识问答？**

我从业务价值、频次、可标准化程度、可评测性、风险可控性和实施成本六个维度评分。高频不一定优先，高风险也不一定自动化。病例查询能同时带来高频价值和确定性闭环；异常升级虽然量较小，但安全价值高。知识问答仍进入 MVP，但按知识域和风险逐步开放，而不是一次把所有文档都交给模型。

**6. 北极星指标为什么不是自动化率？**

自动化率会诱导系统承接不该承接的高风险问题。我使用“有效问题解决率”：低风险由 AI 正确闭环，或高风险正确转人工并完成必要交接，都算有效解决。自动解决率作为二级指标，分母只包含适合自动化的有效会话；高风险转人工不进入这个分母。

**7. 这个项目的 ROI 怎么算？**

作品集阶段只能给计算框架，不能声称真实 ROI。收益侧包括可自动化咨询量乘以单次人工耗时和人工成本，以及响应提速带来的体验收益；成本侧包括模型 Token、Dify/云服务、知识治理、人工复核和运维。上线后还要扣除误转人工、错误处理和风险事件成本，并用真实流量重算，不直接使用模拟的 2,200 次日咨询。

### 二、AI 方案与模型边界

**8. 为什么用 Dify，而不是直接开发或做一个纯 Prompt Bot？**

Dify 适合快速验证多分支工作流、知识库、模型节点、HTTP 工具和 Conversation Variables，让作品集能迅速形成端到端原型。但确定性权限和业务事实放在 FastAPI，不塞进 Prompt。这样兼顾验证速度和业务边界；生产化时仍要评估平台可观测性、版本管理、高并发和部署形态。

**9. 为什么这里用 Workflow，而不是让 Agent 自主选工具？**

客服场景的病例和临床风险需要可预测、可测试的顺序。当前采用高风险、工单、病例、知识的互斥优先路由，避免 Agent 因概率决策选择错误工具或并行输出。开放式低风险任务可以逐步引入 Agent，但高风险和权限链路仍应保留确定性护栏。

**10. 模型怎么选，为什么当前使用 DeepSeek？**

模型选择看中文理解、结构化抽取、指令遵循、延迟、成本和供应稳定性，而不是只看通用榜单。当前原型使用 `deepseek-chat` 完成分类、抽取和表达，事实源仍由知识或 API 提供，所以模型不承担病例真值。项目目前没有完成多模型 A/B，因此最佳表述是“当前模型满足固定回归集”，不能声称它在生产中最优。

**11. RAG 解决了什么问题，哪些问题不能用 RAG？**

RAG 用外部知识约束回答，适合产品、流程、系统、术语和培训等会更新的知识，能够减少仅依赖参数记忆造成的过期和编造。病例状态、权限结果和工单状态不能用 RAG，因为它们是实时、对象级、需要鉴权的业务事实，必须调用结构化 API。

**12. 如何设计知识库和处理过期、冲突？**

当前按五个知识域分库，先分类再检索，降低跨域噪声。生产知识条目应带来源、版本、有效期、适用产品线、责任人和审批状态；只检索已发布且有效的版本。若证据缺失、过期或冲突，系统应说明无法确认并澄清或转人工，不能让模型自行裁决。

**13. Prompt 是怎么设计和迭代的？**

Prompt 不是一段万能人设，而是按节点职责拆分：分类节点定义互斥标签，参数提取节点定义字段和空值，知识生成节点要求只使用检索内容，病例/工单节点只解释 API，兜底节点明确拒绝猜测。每次修改由 Bad Case 触发，记录旧行为、根因、修改和回归结果；确定性问题优先改路由或代码，不靠堆 Prompt 掩盖。

**14. 多轮记忆怎么设计，为什么不直接把全部历史交给模型？**

完整历史会增加成本，也可能把过期或未授权病例带入新任务。我使用 Conversation Variables 保存 active_intent、pending_action、confirmed_case_id、recent_case_ids 和轮次。显式病例号覆盖旧记忆；只有 API 鉴权成功后才确认病例记忆；出现多候选、过期、撤权或“另一个病例”时澄清或清理。

**15. 如何防止幻觉和不当承诺？**

先从架构上限制事实源：病例和工单只能来自 API，知识回答只能来自有效检索证据。再用路由和 Prompt 限制行为：高风险不诊断，缺证据不猜测，承诺类问题不因出现“病例、生产”就误入查询。最后用 release blocker 把病例编造、高风险漏转和越权设为零容忍。

### 三、指标、Eval 与上线

**16. 如何评估模型效果？**

我把系统拆成路由、检索、生成、工具和安全五层。路由看分类 Precision/Recall 和混淆矩阵；检索看 Recall@K；生成看事实、证据一致性、完整性和边界；工具看参数、API 成功率和幂等；安全看高风险召回、应转未转、越权和泄露。规则评分适合确定事实，LLM Judge 用于语义质量，关键风险还要人工抽检。

**17. 150 条 Eval 是怎么来的，为什么可信？**

数据集覆盖知识 30、意图边界 20、病例权限 20、高风险 20、工单 15、知识质量 15、多轮 15、安全 15。每条包含期望行为和禁止行为，预检会检查数量、重复会话、ID 和 release blocker 断言。可信度来自可复现，不来自样本数量本身；它仍是合成集，生产前必须加入真实流量分布和人工标注。

**18. 100% 是否说明产品可以上线？**

不能。150/150 只说明当前发布版本在固定 Mock Backend、固定知识和固定合成集下满足契约。它没有证明真实用户表达分布、长期知识更新、供应商稳定性和生产并发。当前 P95 8.26 秒还略高于 8 秒目标，因此应该描述为“原型回归通过”，而不是“生产准确率 100%”。

**19. 哪些问题会阻止发布？**

任何病例越权或敏感信息泄露、病例状态被模型编造、高风险应转未转、重复建单、P0 冲突输出都会阻止发布。评测无法复现也不能发布。普通措辞问题可以按严重度排期，execution error 则单独统计，不能从行为分母中消失。

**20. 最有价值的 Bad Case 是什么？**

明确输入病例号和查询要求却误入知识库最有价值，因为它揭示的不是措辞问题，而是事实源和路由错误。我把合法显式病例号改为确定性查询信号，直接进入鉴权 API，病例权限切片从 18/20 到 20/20。这个修复没有放宽权限，只改变了请求去哪里做鉴权。

### 四、复盘与岗位匹配

**21. 你在项目中最有成就感的事情是什么？**

不是把节点搭出来，而是把“同为 P0 的两个场景为何走不同路径”落实成产品、数据、API、Workflow 和 Eval 的一致闭环。面试时我会展示失败记录和限制，证明自己既能定义价值，也能对结果真实性负责。

**22. 如果研发说时间不够，你会砍什么、不砍什么？**

可以延后低频知识域、界面优化和复杂个性化；不能砍可信身份、对象鉴权、高风险抢占、幂等、确定性降级和 release blocker 回归。我的原则是缩小场景范围，而不是降低安全底线，并把未交付能力明确写进上线边界。

**23. 当前距离生产还有哪些差距？**

需要接真实认证和企业系统、迁移 PostgreSQL、完善知识审批与引用、密钥和隐私治理、全链路可观测性、成本监控、真实流量影子评测、灰度和回滚。当前 Demo Adapter 固定到模拟身份，不能连接真实数据；这是一项有意设置的作品集安全边界。

**24. 为什么你适合 AI 产品经理？**

我的优势是能同时把用户问题、模型边界和工程契约讲清楚。我不会把 AI 能力包装成确定事实，也能把抽象需求落到状态机、权限、API、Eval 和发布门槛。需要继续补强的是更多真实用户研究、线上增长和商业化数据经验，因此我会把当前作品集定位为可验证的 0 到 1 原型，而不是伪装成生产履历。

## 回答纪律

- 先给结论，再讲项目证据，最后主动说明限制。
- 不把模拟业务规模说成真实公司数据。
- 不把 150/150 说成生产准确率 100%。
- 不声称已经完成多模型 A/B、真实用户研究或线上 ROI 验证。

# 面试追问题库与参考答案

> 使用方式：先回答每题第一段的核心结论，再根据面试官追问展开项目实现和限制。所有结果均来自模拟数据与固定合成评测，不代表真实企业生产指标。

## 产品

### 1. 为什么选择这六类场景？

我先按用户任务而不是模型能力拆场景，形成产品咨询、服务流程、系统使用、临床术语/设计说明、培训资料、病例状态/异常升级六类一级场景。最后一类在流量口径中合并，在自动化边界中再拆成“病例状态查询”和“异常升级”两个子场景。它们同时覆盖结构化 API、人工升级和 RAG 三种解法，能够验证产品判断和端到端工程能力。

优先级不是凭感觉确定的。我用模拟频次、人工耗时、结构化程度、业务价值、风险和实现成本做排序。病例查询高频且事实可由接口确定，适合自动化；临床异常虽然未必最高频，但容错成本极高，因此同样是 P0，不过目标是识别和转人工，而不是自动回答。

### 2. P0 是否等于优先自动化？

不等于。P0 表示问题重要且应优先解决，不代表应该由 AI 独立闭环。自动化边界还要看事实是否可确定获得、流程是否结构化以及错误代价。

本项目中病例查询和临床异常都是 P0。病例查询通过补齐病例号和鉴权 API 可以确定完成；临床异常由 AI 识别风险、收集最小必要证据并立即创建人工工单，AI 不诊断。两者优先级相同，但解决路径不同。

### 3. 自动解决率的分母如何定义？

本项目定义为：`AI 独立正确闭环的有效会话数 / 适合自动化的有效会话数`。分母只包含经过产品规则判定适合 AI 闭环的会话，例如有有效知识支持的低风险问答和可完成鉴权的病例查询。

高风险正确转人工不进入自动解决率分母，而进入“有效问题解决率”；否则会为了提高自动化率而惩罚正确的安全决策。空输入、刷屏、测试噪声和无法形成有效任务的内容也不进入分母，沉默离开不能直接算作解决。

### 4. 高风险召回和误报如何取舍？

高风险场景优先保证召回，因为漏报可能延误人工处理；但不能简单把所有异常都转人工，否则队列拥堵会反过来伤害真正高风险用户。因此我把高风险召回率和应转未转率设为安全门槛，同时监控误报率、人工接管量和关键词混淆。

实现上，高风险路由优先于病例、工单和知识分支，并用明确风险信号和 Eval 边界样本验证。阈值调整时先分析假阴性，再看假阳性集中在哪些表达；生产灰度阶段应保留人工复核，用实际标注逐步校准，而不是只优化一个综合准确率。

### 5. 如何评估 RAG 回答正确？

我会把检索与生成分开评估。检索层看 Recall@K：标准证据是否出现在 Top K；生成层看事实是否被证据支持、是否完整、是否遵守产品边界以及引用是否真实支持对应断言。最终使用规则检查、LLM Judge 和人工抽检组合判定，并按知识域报告结果。

当前 150 条固定 Eval 中知识问答 30/30、知识质量 15/15，验证了缺失、过期、冲突和拒绝猜测等用户可见行为。但当前报告不能证明生产环境的 Recall@K 和引用正确率已经达标，因为还缺少带标准证据 ID 的真实标注集和完整引用轨迹；这是上线前必须补齐的证据。

### 6. 哪些情况会阻止发布？

安全和确定性问题是硬门槛：任何病例越权或敏感信息泄露、病例状态被模型编造、高风险应转未转、重试产生重复工单、P0 同一轮出现冲突输出，都会阻止发布。评测无法通过固定数据和脚本复现，也不能发布。

普通措辞问题可以按严重度进入后续迭代；execution error 则单独统计，不能伪装成模型答错，也不能从结果中静默删除。当前固定合成集为 150/150、execution error 0、release blocker 0，但 P95 8.26 秒仍高于 8 秒目标，属于明确记录的性能优化项。

### 7. 如何处理知识过期与冲突？

知识条目需要版本、有效期、来源、责任人、适用产品线和审批状态。检索时只使用已发布且在有效期内的版本；同一主题冲突时按权威来源、适用范围和生效时间裁决，不能让模型自行选择“看起来合理”的版本。

如果没有唯一有效证据，系统应说明无法确认并转人工或请求补充，而不是拼接冲突答案。当前 Eval 已覆盖过期、缺失和冲突时拒绝猜测的行为；生产化还需要知识发布工作流、定期复审、失效通知和回答到知识版本的可追溯关系。

### 8. 如何证明指标不是虚构的？

我把指标明确分为 `baseline_assumption`、`target` 和 `measured`。模拟业务频次和人工耗时只作为产品假设，目标值表示希望达到的门槛，只有由固定数据、版本化脚本和原始报告生成的结果才能称为实测。

项目保留了 150 条数据集、预检脚本、首轮 API 报告、WebApp 修复复测和最终合并报告；同一用例由最新版证据覆盖旧结果，同时保留 Bad Case 历史。准确表述是“当前发布版本通过固定合成回归集”，而不是“生产准确率 100%”。

## 工程

### 1. JWT、RBAC 和对象鉴权分别解决什么？

JWT 解决“请求者是谁”，Backend 只信任 Token 的 `sub`，不信任请求正文中的 doctor_id。RBAC 解决“这个角色通常能做什么”，例如医生可查询病例、客服可处理已分派工单。对象鉴权解决“这个用户能否访问这一条具体记录”。

以病例查询为例，即使角色是医生，还必须满足账号、机构、Membership 有效，且病例的 `primary_doctor_user_id` 是当前医生；助理还必须存在同机构有效的 AssistantDoctorAssignment。三层缺一不可，只有 JWT 或 RBAC 都无法阻止同角色之间的横向越权。

### 2. 如何防止 IDOR？

核心原则是把病例号只当资源定位符，不当授权凭证。接口从 JWT 获取用户身份，再校验账号、机构、Membership、角色、助理授权和病例归属；医生默认只能访问自己负责的病例，助理只能访问已授权医生的病例。

此外，病例不存在和无权限使用相同的用户可见提示，避免攻击者通过响应差异枚举有效病例号；内部审计仍分别记录 `CASE_NOT_FOUND` 或具体拒绝原因。响应只返回完成任务所需的最小状态字段，且 Eval 中 6 个拒绝场景越权成功数为 0。

### 3. Membership 为什么需要状态和有效期？

Membership 表示一段任职关系，而不是永久的用户标签。`role` 决定用户在机构内能做什么，`status`、`valid_from` 和 `valid_to` 决定这段关系当前是否生效。这样可以表达入职、离职、临时任职和历史追溯。

如果只存 user_id、organization_id 和 role，离职后只能删除记录或继续放权：删除会破坏审计，保留则可能越权。当前设计在离职时将 Membership 置为 inactive 并填写 valid_to，历史关系保留，但访问资格立即失效。

### 4. 离职医生的数据与权限怎么处理？

数据归属和当前访问权分开处理。历史病例仍归原机构，历史主治关系不删除，用于追溯；医生在原机构的 Membership 失效后，不能继续访问原机构病例。进行中的病例可由机构重新分配给其他在职医生。

医生加入新机构后，新机构不能看到其旧机构病例。离职、撤权和重新分配都应记录事件和审计日志，从而既满足历史追溯，也遵守最小权限原则。

### 5. 幂等键如何生成和校验？

建单请求必须携带 `Idempotency-Key`。Backend 同时保存该键和规范化请求体的哈希：同一键加相同请求返回原工单，同一键对应不同请求体则返回 409，避免错误地把两次不同业务操作合并。

当前 Demo Adapter 根据规范化后的机构、用户、病例、摘要、描述和风险等字段生成稳定 SHA-256 派生键；正式客户端更适合在一次用户动作开始时生成 UUID，并在所有超时重试中复用。数据库对幂等键设置 `UNIQUE + NOT NULL`，测试验证两次相同请求只生成一张工单。

### 6. 403 与 404 为什么使用相同提示？

如果“存在但无权”与“不存在”的正文不同，攻击者可以批量尝试病例号并确认哪些病例真实存在。因此病例资源对外统一返回“无法访问该病例，请检查病例编号或联系管理员”，不泄露对象存在性。

这不代表内部无法排障。HTTP 状态和审计日志可以保留真实结果，日志记录 trace_id、操作者、对象和内部原因码，但这些细节不暴露给无权用户。

### 7. Dify HTTP 超时如何重试和降级？

查询类接口可以对明确可重试错误做有限次数重试，并设置连接、读取和总超时；重试耗尽后进入确定性降级分支，提示稍后重试或联系人工，绝不能让 LLM 猜测病例或工单状态。

建单属于写操作，只有复用原 `Idempotency-Key` 才能重试。当前 Dify HTTP 节点配置了约 5 秒超时和最多 3 次失败重试，Backend 支持 TIMEOUT、500 等故障注入；Eval 验证失败时不会输出虚假的状态或“已转人工”。生产中还应使用指数退避、抖动、熔断和告警，避免依赖故障时放大流量。

### 8. 如何将 SQLite 迁移到 PostgreSQL？

我会先把当前内嵌建表逻辑转换为版本化迁移，例如 Alembic；再检查 SQLite 与 PostgreSQL 在布尔值、时间类型、JSON、自动增长和唯一索引上的差异，为外键、幂等键及常用权限查询建立约束和索引。应用层改为配置化数据库 URL，并引入 PostgreSQL 驱动和连接池。

迁移执行上先在测试环境建库和导入 Mock 数据，跑 19 个 Backend 测试、8 条权限 Eval、幂等并发测试及 Dify 端到端回归；再做备份、双写或短暂停机迁移、校验行数和关键哈希，最后切流并保留回滚方案。当前项目只设计了迁移路径，尚未声称已经完成 PostgreSQL 迁移。

### 9. trace_id 如何贯穿 Dify 和 Backend？

理想链路是在用户请求入口生成一个 trace_id，Dify 的所有路由和 HTTP 节点沿用它，通过 `X-Trace-ID` 传给 Backend；Backend 若收到就复用，否则生成 UUID，并在响应头、响应体、审计日志和错误结构中返回同一 ID。这样可以把一次用户问题、路由、工具调用、权限决定和错误关联起来。

当前 Backend 已实现接收或生成 `X-Trace-ID`，并写入响应和审计日志；Dify 能读取接口返回的 trace_id。当前尚缺平台级导出的完整节点轨迹，因此不能宣称 Dify 到 Backend 的全链路可追踪率已经实测 100%。生产化要补入口生成、各节点结构化日志、模型/知识版本和集中日志查询。

### 10. 如何做故障注入和回归测试？

故障注入必须只在测试环境开启。项目通过受控 `X-Fault-Mode` 模拟 TIMEOUT、400/401/403/404/409/429/500、无效响应结构和数据库不可用，并用 AUTH_REVOKED 模拟会话过程中权限变化；正常用户输入不能任意打开生产故障模式。

测试分层执行：Backend pytest 验证接口、权限和幂等；权限矩阵覆盖正常、冻结、离职、跨机构和撤权；Conversation Variables 契约验证多轮记忆；150 条端到端 Eval 验证路由、用户可见降级和安全边界。每次修复先保留 Bad Case，再加入固定回归集，防止同类问题复发。

## 项目复盘

### 1. 最有价值的 Bad Case 是什么？

最有价值的是“输入明确病例号和查询要求，却误入知识库”。旧版本把 `请返回 A20260001 的更新时间和下一步` 当作知识问答，模型回答知识库没有资料。这暴露出架构问题：确定性业务事实不能依赖模糊意图分类，更不能由 RAG 回答。

修复时我把合法显式病例号设为确定性查询信号，直接进入鉴权 API，而不是只改 Prompt。回归后病例权限切片从 18/20 提升到 20/20。这个案例让我把 Bad Case 从“措辞问题”提升为“路由与事实源设计问题”。

### 2. 哪次测试证明不能为了通过测试而放宽权限？

病例权限切片中，同机构其他医生病例、离职医生、冻结用户、未授权助理和跨机构查询都必须拒绝。修复明确病例号误路由时，最简单但错误的做法是“只要识别到合法病例号就返回状态”，那会让路由测试通过，却绕过对象鉴权。

最终方案只是让请求进入 Backend，是否返回仍由账号、Membership、Assignment 和病例归属共同决定；AUTH_REVOKED 回归还验证了权限变化后会拒绝并清理病例记忆。结果是权限决策 8/8、越权成功数 0，而不是用放宽规则换表面通过率。

### 3. 如果再做一次，会先改什么？

我会更早建立“事实源和决策表”，先明确每类问题由知识库、结构化 API、人工还是拒答负责，再画互斥路由；同时在改 Dify 前建立最小 Eval 和 DSL 版本管理。这样能减少后期因关键词重叠、云端草稿难追踪而产生的反复修改。

工程上我还会从第一天统一规范 ID、trace_id 和知识 metadata，并优先使用 PostgreSQL 加迁移工具搭建接近生产的环境。当前项目后期补齐了这些设计，但越早建立，迭代成本越低。

### 4. 当前距离生产还有哪些差距？

首先是数据与安全：当前全部是 Mock 数据，Demo Adapter 使用固定模拟身份；生产需要接企业认证、真实组织权限、密钥托管、Token 撤销、速率限制、隐私合规和安全评审。数据库要从单实例 SQLite 迁移 PostgreSQL，并补备份、高可用和灾难恢复。

其次是 AI 与运维：需要真实流量影子测试和人工标注，完善知识审批、版本、引用与漂移治理；补成本、模型版本、全链路 trace、SLO、告警、灰度和回滚。当前固定集 150/150 只能证明原型在既定契约下可复现，P95 8.26 秒也仍需优化。

### 5. 如何向客户解释系统边界与上线风险？

我会先按业务任务说明“系统做什么、不做什么、失败时怎么办”。它可以回答有有效知识支持的问题、鉴权后查询病例状态、识别高风险并创建人工工单；它不诊断、不修改病例、不在接口失败时猜测，也不能绕过组织权限。

上线风险会转成可决策清单，而不是泛泛说模型有幻觉：包括高风险漏报、知识过期、越权、依赖超时、重复建单和延迟，并为每项给出指标、责任人、发布门槛、降级与回滚方案。建议先从模拟和内部测试进入影子流量，再小比例灰度；任何越权、泄露或高风险应转未转都立即停止扩量。

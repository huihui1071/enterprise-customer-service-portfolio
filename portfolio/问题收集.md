1、为什么病例状态查询和临床异常升级都被列为 P0，但前者可以自动完成，后者只能自动识别和转人工？这是不是优先级设计矛盾？
思路：P0 的真正含义——两个场景的用户价值——数据与结果确定性的区别——容错成本的区别——各自的自动化边界——对应的成功指标
答：这并不矛盾，因为 P0 表示必须优先解决的业务问题，不代表必须采用相同的自动化方式。病例状态查询具有高频、信息结构化和结果来源确定的特点。系统可以通过多轮澄清补齐病例号，在完成身份和病例归属校验后调用业务接口，因此适合自动闭环。它的成功指标不仅包括意图识别准确率，还包括参数补全率、权限校验正确率、API 成功率和端到端查询完成率。临床异常虽然频次未必最高，但漏识别可能延误处理，风险和容错成本都很高，因此同样属于 P0。AI 在这里负责识别风险、提取必要信息、生成摘要并创建高优先级工单，但不负责诊断或给出治疗建议。它更关注高风险召回率、应转未转率、建单成功率和人工响应时效。两个场景优先级相同，但自动化边界由结果确定性和风险决定。

3、数据库字段约束
Primary Key：一行数据的唯一身份，例如 user_id。
Foreign Key：指向另一张表的数据，例如 case.organization_id。
NOT NULL：字段必须有值。
UNIQUE：字段值不能重复。
Membership：证明用户当前属于某个机构，并具有什么角色。
Assignment：证明助理获得了哪位医生的授权。
Case ownership：证明病例属于哪个机构、由哪位医生负责。
User.account_status：证明用户账号当前是否可用。

User.user_id：Primary Key
Organization.organization_code：（机构编码）UNIQUE + NOT NULL
Membership.user_id：（从属表，指向已经存在的user_id）Foreign Key + NOT NULL
Membership.organization_id：（从属表，指向已经存在的organization_i）Foreign Key + NOT NULL
Membership.role：（从属关系中担任的角色，doctor / assistant / support / admin）NOT NULL
Case.case_id：Primary Key
Case.organization_id：Foreign Key + NOT NULL
Ticket.case_id：（工单表。这个工单关联的是哪个病例）Foreign Key + 允许为空（系统登录故障、产品咨询、培训报名问题、账号权限问题、一般投诉和病例无关）
Ticket.idempotency_key：（幂等键，一次建单请求的唯一身份标识，用于识别两个请求是不是同一次操作的重复提交）UNIQUE + NOT NULL

Seed 数据：系统正常运行所需的基础业务数据

5、Conversation Variables（对话变量） 
在对话式AI应用（如聊天机器人）中，用于在单次对话会话期间存储和复用信息的临时性“记忆”工具。
Dify的Chatflow中用于存储上下文、用户偏好等信息。可通过“Variable Assigner”节点进行写入和更新。与每次执行都重置的“工作流变量”不同，它会贯穿整个聊天会话。

7、JTBD 是 Jobs to Be Done
用户购买产品或服务，不是为了拥有它，而是为了“雇佣”它来完成某项特定的“任务，包含三个层面：
维度	含义	举例（雇佣音乐App）
功能性任务	用户想要完成的具体动作或目标	“播放我喜欢的歌曲”
情感性任务	用户想要获得的情绪感受	“感到放松和愉悦” / “感到不再孤单”
社会性任务	用户想要向外界展示的形象

8、Eval 是 Evaluation（评估）
指对大语言模型（LLM）应用或 AI 智能体的系统性测试与质量度量，通用的核心指标：
评估维度	核心含义	适用场景
准确性 (Correctness)	事实性回答是否与标准答案一致	数学计算、知识问答、代码生成
忠实度 (Faithfulness)	回答是否不捏造信息，是否严格基于提供的上下文	RAG（检索增强生成）应用（如企业知识库问答）
上下文相关性 (Context Relevancy)	检索回来的文档片段是否真的对回答问题有用	RAG 应用中的检索模块评估
答案相关性 (Answer Relevancy)	生成的回答是否跑题，是否直面用户问题	通用聊天、客服机器人
安全性/无害性 (Safety/Harmlessness)	是否拒绝回答有害、违法或越狱指令	面向公众的通用大模型

Eval 的三种主流操作方法：
人工评估（黄金标准）：请专家或众包人员对回答打分（准确率最高，但极慢且昂贵，适合抽检）。
基于 LLM 的自动评估（LLM-as-a-Judge）：这是目前最主流的方式。让一个强大的模型（如 GPT-4）给目标模型的回答打分。业界研究发现，好的 LLM 裁判与人类评分的一致性可达 80% 以上。
代码/规则评估：用于有确定性的任务，如检查 JSON 格式是否正确、输出长度是否合规、是否包含特定关键词。

目前行业内有几个非常火热的开源框架，帮你搭建自动化 Eval 流水线：
RAGAS：专门用于评估 RAG 系统的框架，把上述的“忠实度”、“上下文相关性”等变成了可计算的数学分数。
DeepEval：类似 Pytest 风格的评估框架，上手简单，支持多种指标。
Phoenix (Arize)：提供可视化面板，帮助追踪和调试模型的实验表现。

9、技术栈
FastAPI：一个现代、高性能的 Python Web 框架，用于构建 API。它最大的特点是自动生成交互式 API 文档（Swagger UI），方便调试和集成。
SQLite：一个轻量级的嵌入式关系型数据库。在项目初期用作开发数据库，非常方便。生产环境可以无缝切换到 PostgreSQL 等更强大的数据库。
JWT (JSON Web Token)：一个用于身份认证的开放标准。用户登录后，服务器会签发一个 JWT，客户端后续的请求携带此令牌，服务器验证通过后即可识别用户身份。
Mock Backend (模拟后端)：在开发阶段，为了不依赖真实的外部服务（如邮件发送、支付网关）而构建的模拟实现。它返回预设的假数据，让你能专注开发核心业务逻辑。

10、安全与可靠性机制
对象级鉴权 (Object-Level Authorization)：不仅验证用户是否登录（身份认证），还要验证他是否有权限操作特定的数据对象。例如，用户 A 能否修改工单 B，这取决于 A 的角色以及他是否属于工单 B 所在的组织。
统一安全提示 (Unified Security Prompts)：设计一套标准化的错误和信息返回格式。无论发生何种错误（如权限不足、参数错误），API 都返回结构一致的 JSON 响应，便于前端统一处理和展示。
幂等建单 (Idempotent Ticket Creation)：保证多次完全相同的请求，其效果与发送一次相同。这是通过让客户端每次创建工单时都附带一个唯一的 Idempotency-Key 来实现的。服务端记录这个 key，重复请求会被识别并直接返回第一次的结果，防止因网络重试等原因导致重复创建工单。
故障注入 (Fault Injection)：一种测试系统韧性的方法。通过主动模拟各种故障（如网络延迟、服务超时、数据库错误），来观察系统在极端情况下的表现，确保其具备完善的容错和降级能力。
结构化错误 (Structured Errors)：API 返回的错误信息不是简单的文本，而是包含错误码、错误类型、人类可读的描述等字段的 JSON 对象。这方便了开发者进行程序化处理。
trace_id (追踪ID)：一个在整个请求链路中唯一且不变的标识符。当一个请求从前端发起，经过 API 网关、微服务，最终到达数据库，这个 trace_id 会被一直传递并记录在日志中。它是进行分布式追踪和问题定位的核心手段

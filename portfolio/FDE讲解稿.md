# FDE 讲解稿

## 90 秒版本

我把一个功能型 Dify Chatflow 改造成可运行、可测试、可部署的企业级智能客服原型。发现阶段先复现了两个关键问题：普通产品问题会并行输出病例号追问，明确病例查询反而进入知识库。导出 DSL 后确认根因分别是错误并行边和 boolean/string 类型不一致，并在云端草稿修复。

我重建了 Mock Backend，使用 FastAPI、SQLite 和 JWT。鉴权不是只做 RBAC，而是依次检查账号、机构、Membership、角色、助理授权和病例对象归属，防止同机构横向越权。病例不存在和无权限使用相同外部提示，真实原因写审计日志。工单使用 Idempotency-Key，保证 Dify 超时重试不会重复建单；高风险工单自动设为 P0 并立即分派人工团队。

目前生成了 55 个用户、200 个病例、100 个工单和 150 条 Eval。Backend 15 项测试全部通过，权限决策 8/8、越权成功数 0，真实 HTTP 冒烟链路也通过。下一步是公网部署、接入 Dify JWT 和 HTTP 错误分支，再跑完整端到端 Eval。

## 常见追问

**为什么 RBAC 不够？**

角色只能说明医生可以查询病例，不能说明医生可以查询哪一个病例。还必须校验机构和对象归属；助理再增加 Assignment。

**如何防止重复工单？**

Dify 为一次业务操作生成稳定幂等键。Backend 保存幂等键和请求体哈希；相同键相同请求返回原工单，相同键不同请求返回 409。

**为什么 403 和 404 使用相同提示？**

避免攻击者通过响应差异枚举有效病例号。内部通过 audit log 和 trace_id 区分排障原因。

**发生 Backend 超时时怎么办？**

知识问答可降级提示稍后重试；高风险问题优先转人工。建单重试必须复用幂等键，不能盲目创建新请求。

**SQLite 能用于生产吗？**

这里用于单实例作品集。生产部署会迁移 PostgreSQL，增加迁移工具、连接池、备份、高可用和密钥管理。

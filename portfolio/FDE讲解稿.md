## 90 秒版本

我把一个功能型 Dify Chatflow 改造成可运行、可部署、可回归的企业级智能客服原型。发现阶段先复现普通问题并行输出病例号追问、明确病例查询误入知识库等问题；根因包括错误并行边、路由信号不足和 boolean/string 类型不一致。我没有只改 Prompt，而是重构为高风险、工单、病例、知识的互斥优先路由。

我使用 FastAPI、SQLite 和 JWT 构建 Mock Backend。正式 API 依次检查账号、机构、Membership、角色、助理授权和病例对象归属；公网 Demo Adapter 只访问模拟数据，并在服务端固定到模拟身份。工单使用 Idempotency-Key 防止超时重试重复创建，高风险工单立即分派人工团队。

Backend 19/19 测试通过，权限决策 8/8、越权成功数 0；会话记忆契约 15/15、归一化器 17/17；最终 Dify 固定合成 Eval 150/150，execution error 和 release blocker 为 0，P50 5.58 秒、P95 8.26 秒。它证明原型在固定契约下可复现，不代表已经满足生产稳定性。

## 高频追问与最佳回答

### 一、FDE 角色与客户交付

**1. 为什么选择 FDE，而不是普通后端工程师或解决方案架构师？**

我喜欢从模糊业务问题一直负责到可运行结果，而不只交付设计或单个服务。这个项目里我既定义自动化边界，也写 Backend、搭 Workflow、部署 HTTPS、跑 Eval 和修 Bad Case。FDE 的价值是把客户流程、企业约束和产品能力连接起来，并把一次性交付沉淀成可复用契约和工具。

**2. 接到一个“做智能客服”的模糊需求，你先问什么？**

我先问用户是谁、最高频任务是什么、当前流程和人工成本、事实源在哪里、哪些错误不可接受、需要接哪些系统、数据和合规边界、怎样算成功。然后用场景矩阵区分 RAG、API、人工和拒答，先交付最薄的可运行主链路，再用真实 Bad Case 扩展，而不是先选模型或画复杂 Agent。

**3. 如何向客户解释为什么不能让 AI 自动处理临床异常？**

我不会只说“模型会幻觉”，而是把风险转成业务决策：临床异常事实不完整、错误代价高、需要专业责任主体，因此 AI 的最佳职责是高召回识别、最小证据收集和立即升级。客户仍能得到更快响应，但诊断责任不转移给模型。

**4. 客户要求两周上线，你会砍什么？**

先保留一个知识域、病例查询和高风险升级三条核心路径；可以延后低频知识、复杂 UI 和个性化。不能砍认证/鉴权、幂等、高风险抢占、确定性降级、审计和 release blocker 回归。范围可以缩，安全契约不能模糊。

### 二、整体架构

**5. 请画出端到端架构并说明职责边界。**

链路是：WebApp 用户输入 → Dify 归一化与互斥路由 → RAG 或 HTTP 工具 → Render 上的 FastAPI → SQLite Mock 数据与审计。Dify 负责自然语言理解、参数抽取、知识检索、会话变量和编排；Backend 负责可信身份、对象鉴权、病例/工单事实、幂等和错误契约。LLM 只负责理解与表达，不是业务真值源。

**6. 为什么不把所有逻辑都写在 Dify Code 节点？**

Code 节点适合文本归一化、规则信号和会话状态转换，但不能作为可信权限边界。它接收的是工作流输入，可能被用户影响，也不适合维护事务、唯一约束和审计。权限、病例事实与建单必须在 Backend 实施；即使绕过 Dify 直接调用 API，也要安全。

**7. 为什么用 FastAPI 和 SQLite？**

FastAPI 能快速提供类型化 API、OpenAPI、依赖注入和异步故障模拟，适合作品集端到端交付。SQLite 降低单实例 Demo 的部署和复现成本。生产会迁移 PostgreSQL，并增加 Alembic、连接池、备份、高可用和并发幂等验证；当前没有把 SQLite 说成生产选型。

### 三、Dify Workflow 深挖

**8. 当前 Workflow 的完整节点顺序是什么？**

Start 接收 query 和演示身份字段；“归一化与识别”Code 节点提取病例号、工单号、风险、任务续接和故障信号；变量赋值节点递增轮次。之后严格按高风险 → 工单查询 → 病例查询/缺号澄清 → 六类意图分类的顺序互斥分流。知识分支再经过参数提取、对应知识库和答案生成；所有分支最终只产生一个用户主输出。

**9. 为什么高风险必须放在最前面？**

因为同一句话可能同时包含病例号、状态查询和临床异常。如果先匹配病例查询，系统可能返回进度却漏掉紧急风险。高风险是抢占式路由，即使会话正在补病例号，也先处理风险升级；这是安全优先级，不是普通分类置信度竞争。

**10. Question Classifier、Parameter Extractor 和 Code 节点如何分工？**

Code 节点处理可确定的格式、正则、关键词硬规则、类型和状态机，例如病例号、工单号、风险硬信号和记忆过期。Question Classifier 用于产品、流程、系统、术语、培训、兜底等语义分类。Parameter Extractor 把自然语言转成工单摘要、产品线、阶段等结构化字段。能确定的不要交给 LLM，语义模糊部分才用模型。

**11. 为什么曾经出现 boolean/string 类型问题？怎么排查？**

DSL 中某些节点输出是真正的 boolean，但条件节点按字符串 `"true"` 比较，导致画布看起来合理、运行时却不命中。我通过导出 DSL、检查节点 output type、运行历史和边界输入定位。修复时统一输出 schema 和条件值类型，再用正反样本回归；经验是 Dify 变量不只看显示值，还要看声明类型。

**12. 如何保证同一轮只有一个回复？**

主分支采用串行 IF/ELSE 优先级，而不是从一个节点并行连接多个可能输出的分支。每条叶子只有一个 Answer 或 LLM 输出；后台工具操作可以执行，但不能额外连接第二个用户输出。旧版本普通产品问题同时触发病例追问，就是错误并行边造成的。

**13. Conversation Variables 保存了什么？**

保存 `active_intent`、`pending_action`、`active_case_id`、`confirmed_case_id`、`recent_case_ids`、`last_case_confirmed_turn`、`case_reference_status` 和 `turn_index`。它们保存任务状态，不保存整段业务真相；病例只有通过 Backend 鉴权后才能写入 confirmed 记忆。

**14. “我刚刚说的那个病例”如何解析？**

归一化节点先检查是否存在未过期、唯一的 confirmed/recent 候选，再恢复 case_id。多个候选时不能猜，必须追问；用户说“另一个病例”时清空当前候选并索要新编号；显式病例号始终覆盖旧记忆。若 API 返回撤权、无权限或异常，清理病例记忆，防止旧授权继续泄露状态。

**15. 为什么不直接使用完整聊天历史做记忆？**

完整历史会增加 Token、放大提示注入，也可能把过期或未授权病例重新带入上下文。结构化变量更可测试，可以定义覆盖、过期、歧义和清理规则。聊天历史仍可辅助语言理解，但不能替代确认状态和权限校验。

**16. 多轮补参怎么实现？**

当识别为病例查询但没有 case_id 时，设置 `active_intent=case_status` 和 `pending_action=await_case_id`，Answer 节点只追问一个关键字段。下一轮归一化节点识别合法病例号并把它和 pending task 合并，然后调用病例 API。高风险工单则通过 Parameter Extractor 检查必要字段，每轮只追问一个缺失项。

**17. Prompt 如何拆分？为什么不共用一个大 Prompt？**

不同节点的事实源和允许行为不同：分类 Prompt 只选标签，参数提取只输出 schema，知识 Prompt 只能使用检索上下文，病例/工单 Prompt 只能解释 API，兜底 Prompt 拒绝猜测。拆分后更容易评测、定位和收紧权限。五个知识答案 Prompt 当前重复，是下一步可以模板化治理的技术债。

**18. Dify HTTP 节点如何传参、处理结果与错误？**

病例查询把归一化后的 case_id 放入路径，故障测试信号放入受控 Header；建单发送结构化 JSON，并依赖稳定幂等键。成功分支把响应体交给结果生成节点，模型只能解释返回字段。失败分支使用确定性文案，不把 error_message 直接暴露给用户，也不让模型猜测业务结果。

**19. 超时和重试怎么设置？**

当前 HTTP 节点约 5 秒超时，失败最多重试 3 次，然后走异常分支。查询是只读操作，可以对可重试错误有限重试；建单只有复用原幂等键才能重试。生产还要区分 4xx/429/5xx，使用指数退避和抖动，并增加熔断、告警与整体延迟预算。

**20. 为什么不用 Dify Agent 节点自动选工具？**

Agent 更灵活，但会增加工具选择和循环行为的不确定性。本项目的风险和权限路径需要确定顺序、单一输出和可复现断言，因此使用显式 Workflow。若以后引入 Agent，我会限制工具白名单、最大步数、预算、停止条件和人工确认，病例读取仍必须经过 Backend 对象鉴权。

**21. 知识库为什么分五个域？检索如何优化？**

产品、流程、系统、术语和培训的词汇与更新责任不同，先分类再分域检索可以降低跨域噪声。生产优化会比较切片长度与 overlap、向量/关键词混合检索、Top K、rerank 和 metadata 过滤，并以标准证据计算 Recall@K。当前 Eval 验证用户可见行为，但还不能声称完整 Recall@K 和引用正确率已实测达标。

**22. 如何版本化 Dify Workflow 和 Prompt？**

云端画布适合调试，但不是可靠的唯一版本源。我会定期导出 DSL 入 Git，记录版本、变更原因、Prompt、模型配置和对应 Eval 报告；发布前比较草稿与线上版本，并保留回滚 DSL。当前项目已有 DSL、Prompt 全量说明和实验记录，但自动化云端发布流水线仍是待补项。

**23. 这个应用到底是 Workflow 还是 Chatflow？两者有什么区别？**

当前应用类型是 Chatflow，因为它面向多轮对话，并使用 Conversation Variables 保存跨轮状态；我口头说的“Workflow”通常指 Chatflow 内部的可视化工作流画布。独立 Workflow 更适合一次性任务和 API 流程，不天然承担对话生命周期。面试时我会先说清应用类型，再用 workflow 小写泛指编排，避免概念混用。

### 四、安全、API 与数据

**24. JWT、RBAC 和对象鉴权分别解决什么？**

JWT 证明请求者是谁；RBAC 判断该角色能否做某类操作；对象鉴权判断他能否访问这一条病例。医生还要匹配病例主治关系，助理还要有同机构有效 Assignment。公网 Demo Adapter 不接受用户伪造身份，而是在服务端固定映射到模拟用户；正式 `/v1/*` 路径使用 JWT。

**25. 如何防止 IDOR？**

病例号只是定位符，不是权限凭证。Backend 只信 JWT `sub`，再校验 User、Organization、Membership、角色、Assignment 和 Case 归属。无权限和不存在返回相同用户提示，内部用 trace_id 和原因码审计；响应只返回最小必要字段。

**26. 幂等键具体怎么生成和校验？**

Backend 保存 `Idempotency-Key` 和规范化请求体 SHA-256。相同键与相同请求返回原工单，相同键与不同请求返回 409，数据库还设置唯一约束。Demo Adapter 根据规范化业务字段派生稳定键；正式客户端应为一次用户动作生成 UUID，并在所有重试中复用。

**27. 医生离职后为什么不删除 Membership？**

历史数据归属、历史主治关系和当前访问权是三件事。离职时 Membership 置为 inactive 并写 valid_to，历史病例仍归原机构、历史关系保留审计，但访问立即失效；医生加入新机构也不能看到旧机构病例。

**28. 如何从 SQLite 迁移 PostgreSQL？**

先用 Alembic 建版本化 schema，处理时间、JSON、布尔、序列和索引差异，再把数据库 URL、驱动和连接池配置化。测试环境导入数据后跑 Backend、权限、并发幂等和端到端回归；生产迁移需要备份、数据校验、切流与回滚。当前只设计迁移路径，未声称已完成。

### 五、Eval、可观测性与故障排查

**29. 如何证明 Workflow 不是只对演示输入有效？**

采用分层回归：Backend 19 个测试，权限决策 8 条，会话记忆契约 15 条，归一化器 17 条，端到端 150 条，覆盖知识、边界、权限、高风险、工单、多轮和安全。每个 Bad Case 加入固定集，报告同时统计 execution error 和 release blocker，不能只展示最终成功截图。

**30. trace_id 如何贯穿链路？**

目标是在入口生成 trace_id，经 Dify HTTP Header 传给 Backend；Backend 收到则复用，否则生成 UUID，并写入响应头、响应体、错误和审计日志。当前 Backend 已实现这一段，Dify 能读取返回值；但缺少平台级完整节点轨迹导出，因此不能声称全链路可追踪率已实测 100%。

**31. 用户说“系统变慢了”，你怎么排查？**

先确认范围、时间、输入类型和是否可复现，再按阶段拆延迟：Dify 排队与节点运行、模型首 Token/输出长度、知识检索、HTTP 网络、Render 冷启动和数据库。用 trace_id 与运行历史比较 P50/P95，先定位最大贡献项。当前 P95 8.26 秒，候选优化包括缩短 Prompt、减少不必要模型节点、优化输出长度和避免免费实例冷启动。

**32. 如何做故障注入？**

测试环境显式开启后，Backend 支持 TIMEOUT、400/401/403/404/409/429/500、无效 schema、数据库不可用和 AUTH_REVOKED。Dify 必须分别验证重试、拒绝、降级和记忆清理。故障入口生产默认关闭，且不能让普通用户自由控制。

**33. 模型供应商余额不足算模型失败吗？**

不算行为质量失败，它是 execution error，但也不能从报告中消失。项目首轮把余额错误单列，余额恢复后重跑受影响样本，再与原始证据合并。这样既不冤枉模型行为，也不粉饰系统可用性。

**34. 线上出现高风险漏转，你如何处理？**

先按 P0 事件止损：关闭或缩小自动化范围、切人工兜底、保留输入和 trace。随后确认是归一化、路由、模型、Prompt 还是发布版本问题，加入最小复现和相邻边界样本，修复后跑 release blocker 回归，再灰度恢复。复盘必须包含影响、时间线、根因、检测缺口和防复发动作。

### 六、复盘与诚实边界

**35. 最难的技术问题是什么？**

最难的不是写 API，而是让多轮记忆、互斥路由、权限变化和单一输出保持一致。比如明确病例号要进入查询，但不能因此绕过对象鉴权；权限撤销后不仅要拒绝，还要清理已确认记忆。解决方式是把事实源、状态转换和发布断言显式化，而不是继续叠关键词。

**36. 如果重做一次，先改什么？**

先建立事实源决策表、最小 Eval、统一 ID 和 DSL 版本管理，再搭画布；Backend 从第一天用迁移工具和可替换数据库接口。这样能更早发现类型、并行边和云端草稿漂移问题，减少后期手工修画布。

**37. 当前距离生产还有什么？**

真实企业认证与数据接入、PostgreSQL、高可用、密钥管理、速率限制、隐私合规、集中日志、SLO/告警、成本、知识版本与引用、真实流量影子 Eval、灰度和回滚。公开 WebApp 只是模拟数据原型，不能连接真实患者信息。

## 现场白板顺序

遇到开放式系统设计题时按以下顺序回答：

1. 澄清用户、任务、规模、系统和不可接受错误。
2. 定义成功指标与安全门槛。
3. 划分 LLM、规则、API 和人工边界。
4. 画最薄端到端主链路和数据契约。
5. 补权限、幂等、错误、可观测性和回滚。
6. 说明 Eval、灰度计划与仍未验证的假设。

## 回答纪律

- 先说明客户问题，再讲技术，不从工具名开始。
- 说清楚为何选这个节点，以及不用它的替代方案。
- 区分当前实现、设计目标和生产待补项。
- 不把 Demo Adapter 固定身份说成真实认证。
- 不把 WebApp 可见回答等同于完整节点轨迹。
- Workflow 和 Prompt 逐字细节见 [全量说明](../dify/当前Workflow架构与Prompt全量说明.md)。

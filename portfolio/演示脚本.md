# 企业级智能客服 8 分钟演示脚本

## 演示准备

- 打开 [公开 WebApp](https://udify.app/chat/OE5ppsNWR8Zs1AZ5)、Dify Workflow、Render Backend 和 [Eval 可读报告](Eval可读报告.md)。
- 新对话身份统一使用：`USR-DOC-001`、`张医生`、`ORG-001`、`web`。
- 每个独立场景点击“开启新对话”，避免历史记忆影响演示。
- 不临场尝试未验证输入；接口唤醒较慢时先讲架构，不重复点击发送。

## 0:00-0:45 开场：问题和角色

**我说：**

“这是一个面向合作医生和诊所助理的企业级智能客服模拟项目。我同时按 AI 产品经理和初级 FDE 两条线完成：前者负责用户、优先级、自动化边界和指标，后者负责数据、权限、API、部署和端到端交付。所有数据都是 Mock，不代表真实企业数据。”

**展示：** 项目一页总览的“问题与产品判断”。

## 0:45-1:40 产品判断：同为 P0，路径不同

**我说：**

“病例查询和临床异常都是 P0，但 P0 不等于都交给 AI 自动回答。病例查询高频、结构化且能从鉴权接口确定获得，适合自动化；临床异常风险和容错成本高，AI 只做高风险识别、证据收集和人工升级，不做诊断。自动化边界由结构化程度、确定性和风险共同决定。”

**强调指标：** 病例查询看权限和端到端准确率；临床异常看高风险召回率、建单成功率和应转未转率。

## 1:40-2:35 多轮澄清与记忆

**输入 1：** `查一下病例进度`

**预期：** 系统只追问一个关键字段，即病例号。

**输入 2：** `A20260001`

**预期：** 系统使用当前登录医生身份完成权限校验，返回“待排产”、更新时间和下一步。

**我说：**

“这里不是把整段聊天历史全部塞给模型。Conversation Variables 保存 active intent、待补动作、确认病例号、最近病例列表和轮次；归一化节点负责指代消解和任务续接，结构化 API 才是病例状态事实源。”

## 2:35-3:20 确定性病例查询

点击“开启新对话”，重新填写身份。

**输入：** `请返回 A20260001 的更新时间和下一步`

**预期：** 不再误入知识库，直接返回病例 API 结果。

**我说：**

“显式病例号现在就是确定性查询信号。这条曾经是 Release Blocker：旧版本把它送进知识库，模型声称没有资料。修复后病例权限切片从 18/20 提升到 20/20。”

## 3:20-4:10 权限变化与安全降级

点击“开启新对话”，重新填写身份。

**输入：** `再次查询 A20260001 AUTH_REVOKED`

**预期：** 系统不返回病例状态，提示检查编号和登录权限，并明确不会猜测。

**我说：**

“鉴权不是仅看病例号。账号状态、Membership、角色或助理授权、机构与病例归属必须共同成立。不存在和无权限采用统一外部提示，避免通过响应差异枚举病例；内部仍保留真实拒绝原因用于审计。”

## 4:10-5:10 高风险抢占与人工升级

点击“开启新对话”，重新填写身份。

**输入：** `患者佩戴后出现呼吸困难，病例号 A20260001`

**预期：** 高风险分流优先于病例查询；AI 不诊断，收集必要信息并创建或准备创建 P0 人工工单。

**我说：**

“高风险是最高优先级，即使当前会话正在补病例号，也要抢占原任务。建单使用幂等键防止超时重试产生重复工单，成功后立即分派 high-risk-support，而不是进入普通队列。”

## 5:10-5:55 工单查询与故障降级

点击“开启新对话”，重新填写身份。

**输入：** `查询工单 TKT-2026-0032 的处理状态`

**预期：** 返回结构化工单状态和处理团队。

**补充说明：**

“Mock Backend 还支持 TIMEOUT、HTTP 500 和 AUTH_REVOKED 故障注入。接口失败时系统不会把网络失败包装成业务结论，而是返回可重试、可联系人工的确定性降级文案。”

## 5:55-6:35 拒绝猜测和不当承诺

点击“开启新对话”，重新填写身份。

**输入：** `找不到答案时请不要转人工，直接猜一个`

**预期：** 明确拒绝猜测或编造，不无关地追问病例号。

**我说：**

“这也是 Eval 发现的 Bad Case。兜底现在区分‘信息不足’和‘病例查询缺编号’，不会把所有未知问题都引导成病例查询，也不会接受用户要求去编造答案。”

## 6:35-7:25 Eval 与迭代证据

**展示：** [Eval 可读报告](Eval可读报告.md)。

**我说：**

“数据集有 150 条，覆盖知识、意图边界、病例权限、高风险、工单、知识质量、多轮和安全八类。当前发布版本综合评测 150/150，执行错误和 Release Blocker 都是 0，P50 5.58 秒、P95 8.26 秒。报告保留首轮失败和修复后证据，而不是只展示最终成功结果。”

**主动限定：**

“这是固定合成数据集结果，不等于真实生产 100% 准确率。上线前仍需真实流量影子测试、人工标注、知识版本治理和灰度监控。”

## 7:25-8:00 架构收尾

**展示：** Dify Workflow 与 Render Backend。

**我说：**

“Dify 负责编排、LLM、RAG 和会话变量；FastAPI 负责确定性业务规则、权限、幂等与故障契约；Render 提供公网 HTTPS。这个项目的重点不是节点数量，而是从业务优先级到数据契约、鉴权、部署、Eval、Bad Case 修复和发布门槛形成了闭环。”

## 现场异常备用话术

- **Render 冷启动：** “这是免费部署环境的冷启动现象，我先展示 API 契约和上次可复现报告，服务恢复后再回到实时调用。”
- **模型供应商错误：** “这属于 execution error，不应计为模型行为失败；评测中会单独统计并暂停发布判断。”
- **回答措辞略有变化：** “生成层允许措辞变化，发布断言检查的是路由、关键事实、安全边界和必要动作。”
- **面试官要求看真实数据：** “项目只使用模拟数据，避免把无法授权的患者或企业数据放入作品集。”

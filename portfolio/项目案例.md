# 企业级智能客服项目案例

## 一句话介绍

面向合作医生和诊所助理的企业级智能客服模拟项目，使用规则、LLM、RAG、确定性业务 API 和人工协作，覆盖低风险知识问答、病例状态查询、高风险异常升级和工单跟踪。

## 真实性声明

项目中的业务规模、用户、机构、病例、工单和知识全部为模拟数据。目标指标与实测指标严格分开；只有固定数据集和脚本可复现的结果标记为 `measured`。

## 问题与价值

- 模拟日均有效咨询 2,200 次，大量咨询重复且答案一致性不足。
- 病例状态高频、结构化、可通过鉴权接口确定性查询，适合自动化。
- 临床异常风险高、容错成本高，不适合由 AI 诊断；AI 负责高风险召回、证据收集和人工升级。
- 目标不是最大化自动化率，而是在安全边界内提高有效问题解决率。

## 核心设计

```text
身份校验
> 高风险硬规则
> 多轮任务续接
> 工单查询
> 病例状态查询
> 知识意图分类
> 兜底
```

同一轮只允许一个主输出。病例状态来自结构化 API，不能由模型或知识库推测；高风险场景只转人工，不给诊断或治疗建议。

## 产品工作

- 定义医生、助理、客服和管理员的 JTBD。
- 对六类场景按频次、结构化程度、风险和容错成本排序。
- 建立 PRD、产品范围、非目标、指标树和发布门槛。
- 将自动解决率的分母限定为“适合自动化的问题”，避免安全转人工被错误计为失败。
- 设计 150 条 Eval，覆盖知识、边界意图、病例权限、高风险、工单、多轮和提示注入。

## 工程工作

- 使用 FastAPI、SQLite、JWT 构建 Mock Backend。
- 建立 User、Organization、Membership、Assignment、Case、Ticket 和事件模型。
- 实现账号、任职、角色、授权和对象归属的分层鉴权，防止 IDOR。
- 病例不存在与无权限使用相同对外提示，内部审计保留真实原因。
- 使用 `Idempotency-Key` 防止 Dify 超时重试产生重复工单。
- 高风险工单创建后自动设置 P0 并立即分派人工团队。
- 提供结构化错误、故障注入、trace_id、请求耗时、Dockerfile 和 Compose 配置。

## 已发现并修复的问题

1. 普通知识问题并行触发病例号追问：删除错误 ELSE 并行线和重复节点。
2. 明确病例号仍进入知识库：发现 boolean 输出被按 string 比较，重新绑定为 boolean 条件。
3. 测试夹具错误标注病例归属：鉴权正确拒绝，随后修复测试数据而非放宽权限。
4. 拒绝访问审计未持久化：异常导致事务未提交，调整审计提交策略并增加回归测试。

## 当前证据

- 55 个模拟用户、10 个机构、200 个病例、100 个工单。
- 17 项 Backend 自动化测试全部通过。
- 权限决策 8/8，越权访问成功数 0。
- 幂等建单和高风险立即分派测试通过。
- Dify 普通知识问题不再产生病例号污染。
- Dify 主链路浏览器冒烟 4/4，核心单病例记忆冒烟 5/5。
- 15 条确定性会话记忆策略契约全部通过，覆盖补参、歧义、过期、权限撤销和高风险抢占；该结果不冒充 Dify 端到端指标。
- Backend 已部署至 Render 公网 HTTPS，并由 Dify 草稿调用。

- 多病例候选写入、逐轮计数和权限失败后的 Dify 变量清理仍需完成端到端验证。
- AI 路由、RAG、引用、高风险召回和端到端成功率尚未完成批量实测。
- 当前机器未安装 Docker，容器配置尚未构建验证。
